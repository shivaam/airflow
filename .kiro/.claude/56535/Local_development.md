# Apache Airflow 3.x Architecture & Development Guide

## Core Architecture

Airflow 3.x is a distributed workflow orchestration platform with these primary components:

### Runtime Components

| Component | Description | Default Port |
|-----------|-------------|--------------|
| **API Server** | FastAPI-based server serving REST API + React UI | 8080 (28080 via Breeze) |
| **Scheduler** | Parses DAGs, creates DagRuns, schedules TaskInstances | - |
| **Triggerer** | Async event loop for deferrable operators (Triggers) | - |
| **DAG Processor** | Parses DAG files, separate process from scheduler in 3.x | - |
| **Executor** | Runs tasks (Local, Celery, Kubernetes, etc.) | - |
| **Metadata DB** | PostgreSQL/MySQL/SQLite storing all state | 5432/3306 |

### Airflow 3.x Key Changes
- **Decoupled UI**: React frontend served by API server (replaces Flask-based webserver)
- **Task SDK**: Separate SDK for task execution (`task-sdk/`)
- **Execution API**: New API for task execution communication
- **SimpleAuthManager**: Default auth manager (replaces FAB-based auth)

## Breeze Development Environment

Breeze is Airflow's Docker Compose-based development environment. It wraps Docker so you don't
have to manually set up Postgres, Redis, or any of the Airflow components yourself.

### What `breeze` Does
- Builds/pulls the CI Docker image (`ghcr.io/apache/airflow/main/ci/python3.x`)
- Mounts your local source code into `/opt/airflow/` inside the container
- Starts supporting services (Postgres, Redis, etc.) as separate containers
- Drops you into an interactive shell inside the container

**Key mental model**: your code lives on the host, but it runs inside Docker. That's why you
should never run `pytest`, `python`, or `airflow` commands directly on the host -- always go
through `breeze`.

### What `breeze start-airflow` Does
1. Compiles UI assets on the host (runs `pnpm install && pnpm build` via a `prek` hook)
2. Initializes/migrates the metadata database (`airflow db migrate`)
3. Creates admin user (credentials in `dev/breeze/src/airflow_breeze/files/simple_auth_manager_passwords.json`)
4. Starts all components inside Docker via `mprocs` (a terminal multiplexer):
   - API Server
   - Scheduler
   - Triggerer
   - DAG Processor

### Port Mappings (Breeze to Host)

Breeze maps container ports to higher host ports to avoid conflicts:

| Host Port | Container Port | Service |
|-----------|---------------|---------|
| 28080 | 8080 | API Server / UI |
| 25555 | 5555 | Flower (Celery) |
| 25433 | 5432 | PostgreSQL |
| 23306 | 3306 | MySQL |
| 26379 | 6379 | Redis |
| 12322 | 22 | SSH (remote debug) |
| 5173 | - | Vite dev server -- Main UI (host only, dev mode) |
| 5174 | - | Vite dev server -- Auth Manager UI (host only, dev mode) |

### Key Breeze Commands
```bash
breeze                      # Interactive shell (nothing running, you start things manually)
breeze start-airflow        # Start all services (production UI build)
breeze start-airflow --dev-mode  # Start all services + Vite dev servers for hot reload
breeze start-airflow --skip-assets-compilation  # Skip the prek UI build hook
breeze start-airflow --auth-manager fab  # Start with FAB auth manager
breeze down                 # Stop and remove all containers
breeze run pytest ...       # Run tests inside the container
breeze run airflow ...      # Run any airflow CLI command inside the container
breeze build-docs           # Build documentation
```

## UI Architecture

Airflow's UI is NOT a standalone frontend server. The FastAPI API server serves the UI -- similar
to how Django serves templates. In production, the API server serves the pre-built React bundle
from `ui/dist/`. In dev mode, it serves a special `ui/dev/index.html` that points to a Vite dev
server for hot module replacement (HMR).

### Two Separate React Apps

There are two independent React applications that must both be built/running:

| App | Path | Purpose | Dev Port |
|-----|------|---------|----------|
| **Main UI** | `airflow-core/src/airflow/ui/` | The Airflow dashboard (DAGs, runs, tasks, etc.) | 5173 |
| **Simple Auth Manager UI** | `airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui/` | Login page for SimpleAuthManager | 5174 |

Both apps use: React 18 + TypeScript + Vite + Chakra UI

### How `DEV_MODE` Works

The API server checks the `DEV_MODE` environment variable to decide which UI files to serve:

```python
# In core_api/app.py
dev_mode = os.environ.get("DEV_MODE", str(False)) == "true"
directory = _AIRFLOW_PATH / ("airflow/ui/dev" if dev_mode else "airflow/ui/dist")

# In simple_auth_manager.py
dev_mode = os.environ.get("DEV_MODE", str(False)) == "true"
directory = Path(__file__).parent.joinpath("ui", "dev" if dev_mode else "dist")
```

- `DEV_MODE=false` (default): Serves pre-built assets from `ui/dist/` (production build)
- `DEV_MODE=true`: Serves `ui/dev/index.html` which contains `<script>` tags pointing to `localhost:5173` (Vite)

**Important**: `DEV_MODE` applies to BOTH UIs. When enabled, the login page also expects a Vite
dev server on port 5174. You must either run both Vite servers or build the auth manager UI
statically and not use `DEV_MODE`.

### Request Flow

**Production mode** (`DEV_MODE=false`):
```
Browser -> :28080 (API server in Docker)
  -> serves index.html + JS/CSS from ui/dist/
  -> API calls also go to :28080
```

**Dev mode** (`DEV_MODE=true`):
```
Browser -> :28080 (API server in Docker)
  -> serves index.html from ui/dev/
    -> <script> tags point to localhost:5173
      -> Browser fetches JS/CSS directly from :5173 (Vite on host)
      -> Vite HMR websocket also on :5173
  -> API calls still go to :28080
  -> Login page loads from :5174 (auth manager Vite on host)
```

The browser talks to BOTH the API server (28080) and the Vite dev servers (5173, 5174)
simultaneously. That's why all ports must be tunneled when working remotely.

## Starting Airflow -- Three Modes

### Mode 1: Standard (No UI Development)

Use this when you're working on backend code, DAGs, providers, etc. and just need the UI to work.

```bash
breeze start-airflow
```

Access UI at `http://localhost:28080` (login: `admin` / `admin`).

The `prek` hook compiles both UIs into their `dist/` folders automatically.

### Mode 2: Dev Mode with Hot Reload (UI Development)

Use this when you're actively modifying the React UI and want instant feedback.

**If `prek` works on your host** (Node.js compatible with your OS):
```bash
breeze start-airflow --dev-mode
```
This automatically starts Vite dev servers for both UIs on the host.

**If `prek` fails** (e.g., Amazon Linux 2 GLIBC issue -- see Known Issues):
```bash
# Terminal 1 -- Start backend, skip the broken prek hook, but enable DEV_MODE in Docker
breeze start-airflow --dev-mode --skip-assets-compilation

# Terminal 2 -- Main UI Vite dev server (on host)
cd airflow-core/src/airflow/ui
pnpm install
pnpm dev
# Runs on port 5173

# Terminal 3 -- Auth Manager UI Vite dev server (on host)
cd airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui
pnpm install
pnpm dev
# Runs on port 5174
```

Access UI at `http://localhost:28080`. Edit React components and see changes instantly.

### Mode 3: Dev Mode for Main UI Only (Skip Auth Manager Dev Server)

If you're only modifying the main UI and don't need hot reload on the login page, you can build
the auth manager UI statically. However, since `DEV_MODE=true` applies to both UIs, you still
need the auth manager Vite server running OR you need to tunnel port 5174.

The simplest approach is still to run both Vite servers as shown in Mode 2.

### Mode 4: Manual Backend + Vite (Advanced)

For maximum control, start components individually:

```bash
# Terminal 1 -- Breeze shell
breeze

# Inside container:
DEV_MODE=true airflow api-server

# Terminal 2 -- Main UI (on host)
cd airflow-core/src/airflow/ui
pnpm install
pnpm dev

# Terminal 3 -- Auth Manager UI (on host)
cd airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui
pnpm install
pnpm dev
```

Note: This only starts the API server. Scheduler, triggerer, and DAG processor won't be running.
Use this when you only need the UI and API, not full DAG execution.

## Quick Start: Backend-Only on Cloud Desktop (No UI Development)

Use this when you're working on backend code, DAGs, providers, operators, etc. and just need
the Airflow UI to work (no hot reload needed). This is the most common workflow.

### From your Mac

**Step 1 — Sync code to cloud desktop:**
```bash
rsync -avz \
  --exclude='.venv' \
  --exclude='build/' \
  --exclude='__pycache__' \
  --exclude='*.pyc' \
  --exclude='.pytest_cache' \
  --exclude='*.egg-info' \
  --exclude='node_modules' \
  --exclude='dist/' \
  --exclude='.ruff_cache' \
  --exclude='.git' \
  /Users/rastoshi/workplace/airflow/airflow/ \
  rastoshi-2-clouddesk.aka.corp.amazon.com:~/workplace/airflow/airflow/
```

**Step 2 — SSH with tunnel (only port 28080 needed for non-dev-mode):**
```bash
ssh -L 28080:localhost:28080 rastoshi-2-clouddesk.aka.corp.amazon.com
```

### On the cloud desktop

**Step 3 — Build UI assets manually (one-time, or after UI source changes):**
```bash
cd ~/workplace/airflow/airflow/airflow-core/src/airflow/ui
pnpm install && pnpm build

cd ~/workplace/airflow/airflow/airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui
pnpm install && pnpm build
```

Both `dist/` folders must exist or the API server will 500. You only need to rebuild these
when the UI source changes — not on every restart.

**Step 4 — Start Airflow:**
```bash
cd ~/workplace/airflow/airflow
breeze start-airflow --skip-assets-compilation
```

`--skip-assets-compilation` skips the `prek` UI build hook (which fails on AL2 due to GLIBC).
Since we already built the assets in Step 3, the API server will find them in `dist/` and
serve them normally (no dev mode, no Vite servers needed).

Wait for all components (API server, scheduler, triggerer, DAG processor) to show running
in the mprocs UI.

**Step 5 — In a second terminal on the cloud desktop, run any setup commands:**
```bash
cd ~/workplace/airflow/airflow

# Example: add an AWS connection
breeze run airflow connections add aws_default \
    --conn-type aws \
    --conn-extra '{"region_name": "us-west-2"}'

# Verify DAGs loaded (DAGs must be in files/dags/, NOT dags/)
breeze run airflow dags list-import-errors
breeze run airflow dags list

# Trigger a DAG
breeze run airflow dags trigger <dag_id>
```

**Note**: Test DAGs go in `files/dags/`, not `dags/`. See "Adding Test DAGs" section for details.

**Step 6 — Open UI on your Mac:**

Go to `http://localhost:28080`. Login with `admin` / `admin`.

### When to use this vs dev mode

| Scenario | Mode | Tunnel ports |
|----------|------|-------------|
| Backend/DAG/provider work | `--skip-assets-compilation` (build dist/ manually) | 28080 only |
| UI development (hot reload) | `--dev-mode --skip-assets-compilation` + Vite servers | 28080, 5173, 5174 |

## Remote Development Setup (Cloud Desktop to Mac)

When developing on a remote machine (e.g., Cloud Desktop) and accessing the UI from your Mac.

### Step 1: Fix Node.js on the Remote Host

Amazon Linux 2 has glibc 2.26; Node 18+ requires 2.27+. Install a compatible Node via `mise`:

```bash
# Install mise (if not already installed)
curl https://mise.run | sh
echo 'eval "$(~/.local/bin/mise activate bash)"' >> ~/.bashrc
source ~/.bashrc

# Install and activate Node
mise install node@22
mise use -g node@22

# Verify
node --version  # Should show v22.x.x
which node      # Should show ~/.local/share/mise/installs/node/22.x.x/bin/node
```

**Note**: The `mise`-installed Node is used when you run `pnpm` directly in your terminal. The
`prek` hook uses its own isolated Node environment (`language: node` in `.pre-commit-config.yaml`)
which ignores `mise` and still hits the GLIBC error. That's why we use
`--skip-assets-compilation` and run Vite manually.

### Step 2: Start Services on the Remote Machine

**Terminal 1 -- Backend**
```bash
breeze start-airflow --dev-mode --skip-assets-compilation
```

**Terminal 2 -- Main UI Vite dev server**
```bash
cd airflow-core/src/airflow/ui
pnpm install
pnpm dev
```

**Terminal 3 -- Auth Manager UI Vite dev server**
```bash
cd airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui
pnpm install
pnpm dev
```

### Step 3: SSH Tunnel from Mac

```bash
ssh -L 28080:localhost:28080 -L 5173:localhost:5173 -L 5174:localhost:5174 <cloud-desktop-hostname>
```

**Why three ports?**
- `28080`: API server (auth, API calls, serves initial HTML)
- `5173`: Main UI assets + HMR websocket (hot reload)
- `5174`: Login page assets (auth manager UI)

Without 5173, the main UI loads a blank page (JS never arrives).
Without 5174, the login page fails to load and you can't authenticate.

### Step 4: Access UI

Open `http://localhost:28080` in your Mac browser. Login with `admin` / `admin`.

### Port Summary for Remote Development

| Port  | Service                         | Where it runs | Required? |
|-------|---------------------------------|---------------|-----------|
| 28080 | API Server (Docker)             | Remote        | Always    |
| 5173  | Main UI Vite dev server         | Remote (host) | Dev mode  |
| 5174  | Auth Manager UI Vite dev server | Remote (host) | Dev mode  |

## Syncing Code to Remote Machine

If you develop locally and run Airflow on a remote Cloud Desktop, you can sync files with `rsync`.
Be careful not to overwrite `node_modules` or `dist/` on the remote -- those are built with the
remote's Node and should stay intact.

```bash
rsync -avz \
  --exclude='.venv' \
  --exclude='build/' \
  --exclude='__pycache__' \
  --exclude='*.pyc' \
  --exclude='.pytest_cache' \
  --exclude='*.egg-info' \
  --exclude='node_modules' \
  --exclude='dist/' \
  --exclude='.ruff_cache' \
  --exclude='.git' \
  /Users/rastoshi/workplace/airflow/airflow/ \
  rastoshi-2-clouddesk.aka.corp.amazon.com:~/workplace/airflow/airflow/
```

To sync just the DAGs folder:
```bash
rsync -avz dags/ <your-alias>-clouddesk.aka.corp.amazon.com:~/workplace/airflow/airflow/dags/
```

### Better Alternative: VS Code / Kiro Remote SSH

Instead of syncing, you can open the remote folder directly in VS Code or Kiro:

1. Install the "Remote - SSH" extension
2. `Cmd+Shift+P` -> "Remote-SSH: Connect to Host"
3. Enter your Cloud Desktop hostname
4. "Open Folder" -> `~/workplace/airflow/airflow/`

All file edits, terminal, git, and extensions run on the remote machine. No sync needed.

Add this to `~/.ssh/config` for quick access with automatic port forwarding:

```
Host clouddesk
  HostName <your-alias>-clouddesk.aka.corp.amazon.com
  User <your-alias>
  ForwardAgent yes
  LocalForward 28080 localhost:28080
  LocalForward 5173 localhost:5173
  LocalForward 5174 localhost:5174
```

Then just connect to `clouddesk` in VS Code / Kiro -- port tunnels are set up automatically.

## Adding Test DAGs

**IMPORTANT**: Breeze reads DAGs from `files/dags/`, NOT `dags/`.

Inside the container, `scripts/in_container/configure_environment.sh` sets
`AIRFLOW__CORE__DAGS_FOLDER=/files/dags` when the `/files` directory exists (which it always
does in Breeze). The `files/` directory at the workspace root is mounted to `/files/` inside
the container.

```bash
# Create the directory if it doesn't exist
mkdir -p files/dags

# Drop your DAG file there
cp my_dag.py files/dags/

# Verify it's picked up (inside Breeze or via breeze run)
breeze run airflow dags list
```

**Where to put DAGs:**

| Location | Purpose |
|----------|---------|
| `files/dags/` (workspace root) | Local test DAGs, not committed. Mounted to `/files/dags/` in Docker. This is what Breeze actually reads. |
| `airflow-core/src/airflow/example_dags/` | Example DAGs that ship with Airflow (committed to repo) |
| `dags/` (workspace root) | Mounted to `/opt/airflow/dags/` but NOT used by default. Breeze overrides `dags_folder` to `/files/dags`. |

**Syncing just DAGs to a remote machine:**
```bash
rsync -avz files/dags/ <your-alias>-clouddesk.aka.corp.amazon.com:~/workplace/airflow/airflow/files/dags/
```

**Tips:**
- DAGs in `files/dags/` are picked up within a few seconds by the DAG processor
- If a DAG doesn't appear, check for import errors: `breeze run airflow dags list-import-errors`
- Set `is_paused_upon_creation=False` if you want the DAG to start running immediately
- The `files/` folder is gitignored, so your test DAGs won't pollute the repo
- Common mistake: putting DAGs in `dags/` instead of `files/dags/` — they won't be found

## AWS Credentials for Breeze

In Airflow 3.x, tasks run in a separate subprocess via the Task SDK and resolve connections
from the Airflow metadata DB (not from environment variables). Setting `AWS_ACCESS_KEY_ID` etc.
in `init.sh` or `environment_variables.env` won't reach the task — it will fall back to the
EC2 instance metadata (your Cloud Desktop's instance profile), which is the wrong account.

The simplest approach: create the connection via the Airflow UI.

### Step 1: Get credentials on the host

```bash
ada credentials update --account=242508862111 --provider=conduit --role=IibsAdminAccess-DO-NOT-DELETE --once
cat ~/.aws/credentials
```

Copy the `aws_access_key_id`, `aws_secret_access_key`, and `aws_session_token` from the
`[default]` section.

### Step 2: Create the connection in the UI

1. Open `http://localhost:28080` → Admin → Connections
2. Click **+** to add a new connection
3. Fill in:
   - **Connection Id**: `aws_default`
   - **Connection Type**: `Amazon Web Services`
   - **AWS Access Key ID** (Login field): paste `aws_access_key_id`
   - **AWS Secret Access Key** (Password field): paste `aws_secret_access_key`
   - **Extra**:
     ```json
     {"region_name": "us-west-2", "aws_session_token": "<paste aws_session_token here>"}
     ```
4. Save

### Why env vars don't work

- `init.sh` runs before `airflow db migrate`, so `airflow connections add` fails (no DB yet)
- `environment_variables.env` is sourced early enough, but `AIRFLOW_CONN_*` env vars are not
  checked by the Task SDK's `ExecutionAPISecretsBackend` — it queries the API server, which
  reads from the DB
- The `EnvironmentVariablesBackend` is in the worker chain but the env var must be visible in
  the forked task subprocess, which doesn't always inherit from the mprocs-launched services
- Without a valid DB connection, boto3 falls back to IMDS and picks up the Cloud Desktop's
  instance role (`DevEnvInstanceProfile`)

### When credentials expire

STS session tokens expire after ~1 hour. When they do:
1. Refresh on the host: `ada credentials update --account=242508862111 --provider=conduit --role=IibsAdminAccess-DO-NOT-DELETE --once`
2. Copy fresh values from `cat ~/.aws/credentials`
3. Edit the `aws_default` connection in the UI with the new values

The connection persists in the DB across breeze restarts (unless you run `breeze down`, which
destroys volumes). After `breeze down`, you'll need to recreate it.

## Running with FAB Auth Manager

If you need the Security menu (Users, Roles, Permissions), use the FAB auth manager:

```bash
# Start Breeze shell
breeze

# Inside container - run these commands in order:

# 1. Enable FAB auth manager
export AIRFLOW__CORE__AUTH_MANAGER=airflow.providers.fab.auth_manager.fab_auth_manager.FabAuthManager

# 2. Create admin user (first time only, or after db reset)

  --email admin@example.com --firstname Admin --lastname User

# 3. Start API server
DEV_MODE=true airflow api-server
```

Access UI at http://localhost:28080 with `admin/admin`. The Security menu will appear in the navbar.

**Note**: If you get auth errors, reset the DB first with `airflow db reset -y` before creating the user.

## Known Issues

### Amazon Linux 2 + Node.js (GLIBC Error)

AL2 ships glibc 2.26; Node 18+ requires 2.27+. Symptoms:
```
node: /lib64/libc.so.6: version `GLIBC_2.27' not found (required by node)
```

**Fix**: Install Node via `mise` (see Remote Development Setup above).

**Caveat**: The `prek` hook `compile-ui-assets` uses its own Node environment via `pre-commit`'s
`language: node` runtime, which ignores `mise` and still fails. Workaround:
- Use `--skip-assets-compilation` with `breeze start-airflow`
- Run `pnpm install && pnpm build` (or `pnpm dev`) manually in your terminal where `mise` Node is active

### UI Not Found Errors (500 Internal Server Error)

If you see `TemplateNotFound: '/index.html'` or a 500 error on the root page:

1. **Without dev mode**: The UI hasn't been built. Build it:
   ```bash
   cd airflow-core/src/airflow/ui && pnpm install && pnpm build
   cd airflow-core/src/airflow/api_fastapi/auth/managers/simple/ui && pnpm install && pnpm build
   ```

2. **With dev mode**: The Vite dev servers aren't running. The API server is trying to serve
   `ui/dev/index.html` which points to `localhost:5173`, but nothing is listening there.
   Start the Vite dev servers manually (see Mode 2 above).

3. **`--skip-assets-compilation` without `--dev-mode`**: The `DEV_MODE` env var isn't set inside
   Docker, so the API server looks for `ui/dist/` which doesn't exist. Use
   `--dev-mode --skip-assets-compilation` together to set `DEV_MODE=true` while skipping the
   broken `prek` hook.

### Login Page Not Loading (port 5174 errors)

If you see `ERR_CONNECTION_REFUSED` for `localhost:5174` on the login page:
- `DEV_MODE=true` makes the auth manager UI also expect a Vite dev server on port 5174
- Either start the auth manager Vite server, or tunnel port 5174 if working remotely

### DAG Processor Crash: "Team does not exist" After DB Reset

**Symptom**: After `breeze down` + `breeze start-airflow`, the DAG processor and scheduler crash
immediately with:
```
AirflowConfigException: Invalid config for section `dag_processor` key `dag_bundle_config_list`.
Team 'team_alpha' does not exist
```

**Root cause**: The `files/airflow-breeze-config/init.sh` script on the host sets
`AIRFLOW__DAG_PROCESSOR__DAG_BUNDLE_CONFIG_LIST` with `team_name` references (e.g., `team_alpha`,
`team_beta`). After a DB reset, the `team` table is empty but the init script still injects
those team references on every container startup.

`breeze down` removes Docker volumes (including the DB), but `files/` is a host directory — not
a Docker volume — so the init script survives.

**Fix**: Rename or edit the init script on the host:
```bash
mv files/airflow-breeze-config/init.sh files/airflow-breeze-config/init.sh.bak
```
Or remove just the `DAG_BUNDLE_CONFIG_LIST` export from the script if you still need the other
settings. Then restart Breeze.

## Breeze `files/` Directory (Host-to-Container Config Injection)

Breeze mounts the `files/` directory at the workspace root to `/files/` inside the container.
This directory is gitignored (`/files` in `.gitignore`) and is your personal scratch space for
injecting config into the Breeze container.

### Auto-sourced init script

If `files/airflow-breeze-config/init.sh` exists, Breeze sources it on every container startup
(via `scripts/in_container/run_init_script.sh`). This is useful for setting custom env vars,
Airflow config overrides, or running setup commands.

**Example** — override the executor and DAG bundle config:
```bash
#!/usr/bin/env bash
export AIRFLOW__CORE__EXECUTOR="LocalExecutor"
export AIRFLOW__DAG_PROCESSOR__DAG_BUNDLE_CONFIG_LIST='[{"name": "dags-folder", "classpath": "airflow.dag_processing.bundles.local.LocalDagBundle", "kwargs": {"path": "/opt/airflow/dags"}}]'
export AIRFLOW__CORE__LOAD_EXAMPLES=False
```

### Gotcha: survives `breeze down`

Since `files/` lives on the host filesystem (not in a Docker volume), `breeze down` does NOT
touch it. If you have stale config in `init.sh` that references DB state (like teams, connections,
or pools), a DB reset will cause mismatches. Always check `files/airflow-breeze-config/init.sh`
when debugging unexpected config after a `breeze down`.

### Other uses

You can put any files in `files/` and access them at `/files/` inside the container — test data,
SQL scripts, credential files, etc.
